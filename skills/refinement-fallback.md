# 按请求推敲，而非套模板

先读原文，判断用户打算让下一位助手做什么、已有多少信息、语气和限制是什么。不要把任务分类当成结论。

若是观点或学术讨论，考虑论点、前提、证据、反例如何影响问题；若是写作，考虑读者、目的与原声，避免把私人短消息改成公文；若是界面，思考具体动作、反馈与信息层次；若是工程，关注现有行为与希望改变的行为及必要验证；若是研究，确定问题、资料边界与可追溯证据。仅选择与本次请求有关的思考步骤。

保留原文事实和否定约束。缺少信息时判断它是否真的会改变结果，再决定是否提出少量澄清或保留条件表达。不要虚构用户没有给出的背景，也不要为显得完善添加预算、周期或清单。

短而开放的请求应得到实质完善，不因为信息少就只做同义改写：选出对这条需求最有帮助的内容，例如想解决的具体问题、已有资料如何利用、可比较的方向或可行动的下一步。用条件或可选建议处理合理推测，不把缺失事实补成确定背景，也不强制补齐任何固定栏目。

最后选择适合原请求的表达形式。明确要求一句话、口语或直接改写时保持简短；长请求去重并理清关系。原文短不是少思考的理由，正文长也不是有效完善的证明。此技能用于编辑 Prompt，不代用户执行原任务。
